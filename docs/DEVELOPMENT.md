# 开发与验收

## 接手入口

先读 [架构](ARCHITECTURE.md)、[README](../README.md) 和涉及模型时的 [Agent 协议](AGENT-PROTOCOL.md)，再查看对应源文件与测试。问题说明应包含触发条件、当前行为、期望行为与虚构复现样例。

## 一次变更

1. 查看 `git status`，在独立分支处理一个具体问题，保留已有未提交工作。
2. 修复逻辑缺陷时，先用虚构数据复现并补充能捕捉该缺陷的回归测试。纯文档或视觉调整检查链接、排版与实际显示。
3. 完成修改后运行下面的验证命令。UI 改动还需在 Chrome 中加载扩展，用虚构资料和 `fixtures/form.html` 验收，并记录截图及操作结果。
4. PR 说明写明用户可见变化、验证结果和未验证范围。检查结果与实际提交保持一致。
5. 合并后复核 CI；发布时核对 manifest/package 版本、扩展目录和下载包。不要把仓库内旧 ZIP 当作本次构建产物。

```sh
npm ci
npm test
npm run check
npm run package
```

## 需要持续保持的行为

- 默认离线；可选 API 由用户主动发送并按来源授权。
- 模型只建议映射，建议导入后由用户勾选；资料值来自本地。
- 保留已有值，证件号码单独允许；填写结果回读验证。
- 上传、验证码、协议和最终提交保留本人操作。
- 测试、截图、issue 和仓库只使用虚构资料，不收录真实简历、凭据和带令牌的申请链接。

## 自动化的下一阶段

参见 [Magpie 研究](MAGPIE-WORKFLOW.md)。现有 Actions 已在 push/PR 上执行测试、静态检查、打包和产物上传。优先增加真实 Chromium 的虚构表单验收与 PR 截图，再考虑反馈巡检和版本发布自动化。

建议将反馈处理分成可追溯状态：待复现 → 已复现 → 修复分支 → 验证通过 → 待发布 → 已发布。为每项反馈记录来源、提交和测试证据，避免重复处理。定时巡检、对外回复、自动合并与发布尚未启用；配置具体范围与凭据后再实施。
